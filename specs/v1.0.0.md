## Introduction

OireMark is a plain-text formatting language designed for authoring documents ranging from quick notes to wiki-scale documentation and books.

### Core Principles

1. **Explicit over implicit.** Markers are self-describing: `h3.` clearly indicates a level-3 heading.
2. **No invisible syntax.** Unlike some other markup languages, OireMark never requires indentation or counting characters. Trailing spaces have no semantic meaning.
3. **Consistent structure.** Block elements use `[tag]...[/tag]` delimiters. The only exception is the fenced form of code blocks (Section 10).
4. **Strict parsing.** Malformed structure (an unclosed block, invalid nesting, a feature outside the active profile) is an error, not a guess. Text that merely resembles markup (a tag in the wrong case, an unpaired formatting marker) is not markup and renders literally.
5. **No generated words.** The parser never adds human-language text to the output. Every title, label and caption is written by the author and is visible, so sighted and screen reader users get the same information, and implementations need no translation tables.

### Conventions

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** and **MAY** are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) when, and only when, they appear in all capitals.

### Character Encoding

- **UTF-8 is required.** No other encodings are supported.
- **BOM:** If present at the start of the document, parsers MUST strip it. Output MUST NOT contain a BOM. U+FEFF anywhere else is an ordinary character.
- **Invalid UTF-8:** Parsers MUST reject the document with an error.
- **Line endings:** LF, CRLF and CR are all accepted and each counts as one newline.

### Case Sensitivity

All OireMark syntax is case-sensitive. Tags must be lowercase:
- `[note]` — valid
- `[Note]` or `[NOTE]` — not a tag, renders literally

### Typography

Characters are output exactly as written. OireMark does not turn `--` into a dash, `...` into an ellipsis, or straight quotes into curly ones: the correct characters depend on the language, and UTF-8 lets authors type them directly.

Parsers MUST NOT make typographic replacements by default. They MAY offer them as an option that is off by default; output produced with such an option is outside the conformance tests.

## 1. Document Metadata

Optional block at document start for language, profile, and future extensions:

```
[meta]
lang: uk
profile: standard
title: My Document
author: André Polykanine
[/meta]
```

The `lang` value sets the document's primary language (BCP 47 / ISO 639-1 code). Parsers SHOULD output it as the root `lang` attribute.

The `profile` value specifies which parser profile to use (see Section 23). If omitted, parsers use their configured default profile.

### Recognized Keys

| Key | Purpose | Output |
|-----|---------|--------|
| `lang` | Document language | `<html lang="...">` or root element attribute |
| `profile` | Parser profile | Controls feature availability |
| `title` | Document title | `<title>` in `<head>` if generating full HTML |
| `author` | Document author | `<meta name="author">` if generating full HTML |

Implementations MAY define additional keys. Unrecognized keys MUST be ignored, and parsers SHOULD warn about them.

### Syntax Rules

- One key-value pair per line
- Format: `key: value`
- Keys are case-sensitive and lowercase
- Leading/trailing whitespace around values is trimmed
- Empty lines within `[meta]` are ignored

**Placement:** If present, `[meta]` MUST be the first element in the document. Only blank lines and `[comment]` blocks may precede it. Any other content before it, or a `[meta]` anywhere later (including inside a container), is a `meta-not-first` error.

**Profiles:** `[meta]` is read in every profile except `inline`. It is read before the profile is applied, which is what lets it choose one.

## 2. Whitespace Rules

### Core Principle

In OireMark, **indentation and trailing spaces have no semantic meaning**, but **newlines are significant**.

This ensures:
- No invisible syntax that screen readers cannot announce
- No accidental formatting from copy-paste or editor behavior
- Predictable parsing regardless of indentation style

### Newline Significance

Newlines determine:
- Line breaks within paragraphs (single newline → `<br>`)
- Paragraph boundaries (blank line → new `<p>`)
- List item boundaries
- Block element boundaries

A line containing only whitespace counts as a blank line.

### Line Preparation

Before parsing, outside code blocks:

- Trailing whitespace is removed from every line. An escaped space at the very end of a line is removed with it, leaving a literal backslash.
- Blank lines and newlines at the end of the document are ignored.

Whitespace inside a line is kept as written.

### Block Element Line-Start Requirement

Block-level tags MUST begin at the start of a line; leading whitespace is ignored. Content before a block tag on the same line is invalid:

```
h2. Valid Heading

Some text [quote]Invalid — block tag mid-line[/quote]
```

The second line produces a parse error.

A closing block tag (`[/note]`, `[/quote]`, and so on) MUST also stand on its own line. A closing tag with no matching open block is a `mismatched-tag` error. Placement is checked first: `Text [/note]` is a `block-tag-mid-line` error whether or not a note is open. (`[/lang]` is the exception, because it can also close an inline span; see Section 17.)

**Block syntax subject to this rule:**
- `[quote]`, `[note]`, `[more]`, `[def]`, `[code]`, `[fn]`, `[meta]`, `[comment]`, `[toc]`, and block `[lang]`
- Headings (`h1.` through `h6.`)
- List markers (`*`, `-`, `#`, `1.`, and their nested forms)
- Definition list markers (`;`, `:`)
- Table rows (`|`, `||`)
- Horizontal rules (`---`)
- Short form quotes (`>`)
- Code fences (```` ``` ````)

### Inline vs. Block Determination for [lang]

The `[lang]` tag can produce either inline (`<span>`) or block (`<div>`) output based on content structure:

**Inline** — content on the same line as opening tag:

```
Here is [lang fr]texte en français[/lang] in English.
```

**HTML:** `<p>Here is <span lang="fr">texte en français</span> in English.</p>`

**Block** — newline after opening tag:

```
[lang fr]
Ceci est un paragraphe entier en français.
Avec plusieurs lignes.
[/lang]
```

**HTML:**

```html
<div lang="fr">
  <p>Ceci est un paragraphe entier en français.<br>
  Avec plusieurs lignes.</p>
</div>
```

### Block [lang] Rules

When `[lang]` is block-level:
- It MUST start at the beginning of a line (no preceding content)
- It may contain paragraphs, lists, and other block elements allowed in its profile
- The closing `[/lang]` MUST also be on its own line

**Invalid:**

```
Some text [lang uk]
Текст українською.
[/lang]
```

This produces an error — block `[lang]` has content before it on the line.

### Indentation Is Ignored

These are equivalent:

```
[note]
This is a note.
[/note]
```

```
[note]
    This is a note.
[/note]
```

Both produce identical output. The indentation is not preserved or meaningful.

**Exception:** Inside code blocks, all whitespace including indentation is preserved literally.

## 3. Headings

```
h1. Main Title
h2. Subtitle
h3. Section Heading
h4. Subsection
h5. Minor Heading
h6. Smallest Heading
```

The marker MUST be followed by a space. `h2.Title` is not a heading but an ordinary paragraph; since it is almost always a typo, parsers SHOULD warn about it.

### Custom IDs

```
h2. My Section {#custom-id}
```

**HTML output:**

```html
<h2 id="custom-id">My Section</h2>
```

### Auto-Generated IDs

If no custom ID is provided, parsers MUST generate one from the heading text:

```
h2. Hello World
h2. Огляд проєкту
```

**HTML output:**

```html
<h2 id="hello-world">Hello World</h2>
<h2 id="огляд-проєкту">Огляд проєкту</h2>
```

**Slugification rules**, applied in order:
1. Strip inline formatting markers, keeping their text.
2. Normalize to Unicode Normalization Form C (NFC), so text that looks the same always gives the same ID.
3. Convert to lowercase with the default Unicode mapping, independent of any locale. (A Turkish system setting must not change `I` into `ı`.)
4. Replace each run of whitespace with one hyphen.
5. Remove every character that is not a Unicode letter, combining mark or digit (General Categories L, M and N), or a hyphen. Text in any script is kept.
6. Collapse multiple hyphens into one and remove leading and trailing hyphens.
7. If the result is empty, use `section`.

The resulting IDs are valid HTML: HTML requires only that an ID is unique, not empty, and free of whitespace. Browsers follow links to them both as written (`#огляд-проєкту`) and percent-encoded (`#%D0%BE%D0%B3…`).

### Unique IDs

All IDs in a document share one namespace: custom heading IDs, generated heading slugs, and the IDs generated for notes, tables of contents and footnotes.

- Two identical custom IDs are an error.
- Custom IDs and footnote IDs (`fn1`, `fnref1`, and so on) are fixed: they are reserved for the whole document before any other ID is generated, wherever they appear.
- A generated heading, note or table-of-contents ID that collides with a reserved ID, or with a generated ID earlier in the document, gets `-2`, `-3`, and so on: the first suffix not yet taken.

```
h2. Intro
h2. Setup {#intro}
```

**HTML:**

```html
<h2 id="intro-2">Intro</h2>
<h2 id="intro">Setup</h2>
```

### Inline Formatting in Headings

Headings may contain inline formatting:

```
h2. Introduction to *OireMark*
```

**HTML:** `<h2 id="introduction-to-oiremark">Introduction to <strong>OireMark</strong></h2>`

## 4. Paragraphs and Line Breaks

- **Single line break** → `<br>`
- **Blank line** (two or more consecutive newlines) → new `<p>`
- **Multiple blank lines** → collapse to single paragraph break

```
This is line one.
This is line two, same paragraph, with a line break before it.

This is a new paragraph.
```

**HTML output:**

```html
<p>This is line one.<br>
This is line two, same paragraph, with a line break before it.</p>
<p>This is a new paragraph.</p>
```

A line that begins another block element (a heading, list item, definition marker, table row, short form quote, block tag, code fence or horizontal rule) ends the paragraph without a blank line:

```
Shopping list:
* Milk
* Eggs
```

**HTML:**

```html
<p>Shopping list:</p>
<ul>
  <li>Milk</li>
  <li>Eggs</li>
</ul>
```

## 5. Inline Formatting

| Syntax | Element | HTML |
|--------|---------|------|
| `*bold*` | Strong | `<strong>bold</strong>` |
| `_italic_` | Emphasis | `<em>italic</em>` |
| `__underline__` | Underline | `<u>underline</u>` |
| `-deleted-` | Deletion | `<del>deleted</del>` |
| `+inserted+` | Insertion | `<ins>inserted</ins>` |
| `~subscript~` | Subscript | `<sub>subscript</sub>` |
| `^superscript^` | Superscript | `<sup>superscript</sup>` |
| `=key=` | Keyboard | `<kbd>key</kbd>` |
| `==highlight==` | Mark | `<mark>highlight</mark>` |
| `` `code` `` | Code | `<code>code</code>` |

### Nesting

Inline formats may nest if properly paired:

```
*_bold italic_*
```

**HTML:** `<strong><em>bold italic</em></strong>`

An element cannot nest inside itself: in `*outer *inner* outer*`, the second `*` is literal, so the first and third pair up and the last is left over:

**HTML:** `<strong>outer *inner</strong> outer*`

### Strict Pairing

Overlapping markers are invalid and render literally:

```
*_bad overlap*_
```

**Output:** Literal `*_bad overlap*_`

Markers pair only within one line. `*bold` on one line and `text*` on the next are both literal.

### Marker Boundaries

A marker only formats text when it sits at a word boundary.

An **opening** marker:
- MUST be immediately followed by a non-whitespace character, and
- MUST NOT be immediately preceded by a letter or digit.

A **closing** marker:
- MUST be immediately preceded by a non-whitespace character, and
- MUST NOT be immediately followed by a letter or digit.

The content between an opening and a closing marker MUST NOT be empty: `--`, `**` and `==` on their own are literal text.

"Letter" and "digit" mean any character of Unicode General Category L (letters), M (combining marks, such as the stress mark in `сло́во`) or N (numbers), so the rule behaves the same in every script. "Whitespace" means any character with the Unicode White_Space property, including the non-breaking space. A character produced by an escape counts as itself: in `\\*bold*`, the `*` follows a backslash, not a letter, so it opens.

**Exception:** subscript `~` and superscript `^` are exempt from the letter-or-digit conditions, because they belong inside words: `H~2~O`, `E=mc^2^`.

A marker that does not meet these conditions is literal text:

```
* not bold *                → literal (spaces inside markers)
*also not bold *            → literal (space before closing marker)
well-known and self-evident → literal (hyphens inside words)
snake_case_name             → literal
a=b and c=d                 → literal
2*3*4                       → literal
=Ctrl+Alt+Del=              → <kbd>Ctrl+Alt+Del</kbd>
H~2~O and E=mc^2^           → H<sub>2</sub>O and E=mc<sup>2</sup>
```

### Marker Runs

`__` (underline) and `==` (highlight) are recognized before the single `_` and `=`, so `__word__` is underlined, not doubly italic.

A run of one marker character longer than the marker it forms is literal: `**bold**`, `___x___`, `===` and `++x++` are not formatted. (Bold in OireMark is a single `*`.)

### Inline Code

A code span opens with a run of one or more backticks and closes at the next run of exactly the same number of backticks on the same line.

- Everything inside is literal: no formatting, no escapes. A backslash is an ordinary character.
- If the content both begins and ends with a space, and is not made only of spaces, one space is removed from each side. This lets code begin or end with a backtick.
- If no matching closing run appears on the same line, the backticks are literal text.
- Code spans are not subject to the marker boundary rules and may appear anywhere, including inside words.
- Outside a code span, a backslash-escaped backtick (`` \` ``) is a literal backtick and cannot open a code span.

```
`print()`            → <code>print()</code>
`C:\Users\`          → <code>C:\Users\</code>
`` a`b ``            → <code>a`b</code>
`` `quoted` ``       → <code>`quoted`</code>
```

### Pairing Algorithm

Each line is processed in this order:

1. **Code spans** are found first, left to right. Their content is never parsed for anything else.
2. **Escapes** are applied to the remaining text. Escaped characters are literal and never act as markers or brackets.
3. **Bracketed constructs** are found next: links, images, footnote references and inline `[lang]` spans. Their URLs are literal. The text inside a link or a `[lang]` span is paired on its own: a marker inside it never pairs with one outside it.
4. **Formatting markers** are paired by one left-to-right pass with a stack of open spans. For each marker:
   - If it meets the closing conditions and a span of the same kind is open:
     - if that span is the innermost open one, the marker closes it;
     - otherwise the spans overlap: that opener, every opener above it on the stack, and this marker all become literal text.
     In both cases the content between the two markers must not be empty; if it is, the marker does not close.
   - Otherwise, if it meets the opening conditions and no span of the same kind is open, it opens a new span.
   - Otherwise it is literal text.
5. Openers still unclosed at the end of the line (or of the link text or span) are literal text.

For the boundary conditions, a code span, link, image or footnote reference next to a marker counts as punctuation: `` *`code`* `` and `*[docs]:https://example.com*` are bold.

Because closing is tried first, a marker that could either close or open closes: in `H~2~SO~4~`, the second `~` closes the first subscript.

## 6. Escaping

A backslash `\` followed by any ASCII punctuation character produces that character literally:

```
!"#$%&'()*+,-./:;<=>?@[\]^_`{|}~
```

```
\*not bold\*
\[not a tag\]
This is a backslash: \\
1984\. A good year.
\# Not a list item
h2\. Not a heading
```

### Non-Breaking Space

A backslash followed by a space produces a non-breaking space:

```
10\ 000
```

**HTML:** `10&nbsp;000`

An escaped space is never trimmed, so `| \ |` produces a table cell containing a non-breaking space. A literal non-breaking space character (U+00A0) typed directly is also preserved.

### Other Backslashes

A backslash followed by anything else (a letter, a digit, a non-ASCII character, or the end of a line) is a literal backslash. `\n` and `\t` are literal text; they do not produce newlines or tabs.

### Where Escapes Do Not Apply

Escapes are not processed inside code spans, code blocks, comments, or URLs.

## 7. Links

### Basic Syntax

```
[Link text]:url
[url]
```

### Where a URL Ends

These rules apply to every URL after a `:`, in links and images alike. A URL starts right after the `:` and ends at the first whitespace character, at the end of the line, or (inside link text, as in a linked image) at an unbalanced `]`. Then the following are removed from its end, repeatedly, until none applies:

- A trailing `.`, `,`, `;`, `:`, `!`, `?`, `'` or `"`.
- A trailing formatting marker character (`*`, `_`, `-`, `+`, `~`, `^`, `=`), so a link can end a formatted span: `*see [docs]:https://example.com*`.
- A trailing `)`, unless the URL contains a matching `(`.

So `(see [the guide]:https://example.com/guide.)` links to `https://example.com/guide`.

A URL is fully literal: no formatting and no escapes are processed inside it.

In a self-link (`[url]`), the whole bracketed text is the URL and nothing is removed.

```
See [the guide]:https://example.com/guide.
Read [the article]:https://en.wikipedia.org/wiki/Mercury_(planet), then continue.
```

**HTML:**

```html
<p>See <a href="https://example.com/guide">the guide</a>.</p>
<p>Read <a href="https://en.wikipedia.org/wiki/Mercury_(planet)">the article</a>, then continue.</p>
```

A URL that genuinely ends in one of those characters, or contains a space, must percent-encode it (`%2E`, `%20`).

### URL Handling

OireMark auto-detects and normalizes common URL patterns so users don't need to know technical protocols.

#### Auto-Detection Rules

| User writes | Parser normalizes to | Example |
|-------------|---------------------|---------|
| `www.example.com` | `https://www.example.com` | `[Visit site]:www.example.com` |
| Email address | `mailto:address` | `[Contact us]:hello@example.com` |
| Explicit scheme | Unchanged | `[Call]:tel:+1234567890` |
| Relative path | Unchanged | `[About]:/about` |
| Anchor | Unchanged | `[Top]:#top` |

#### Email Detection

An email address is detected when it:
- Contains exactly one `@`
- Has non-empty text before the `@`
- Has text after `@` containing at least one `.`

Examples that trigger email detection:
- `hello@example.com` → `mailto:hello@example.com`
- `support@mail.company.org` → `mailto:support@mail.company.org`

Examples that do NOT trigger email detection:
- `@mention` — no text before `@`
- `price@50` — no `.` after `@`
- `mailto:hello@example.com` — already has scheme

#### Scheme Detection

A URL has an explicit scheme if it starts with a scheme name followed by `:` (e.g., `https://`, `mailto:`, `tel:`, `custom://`). A scheme name, as in RFC 3986, is a letter followed by any number of letters, digits, `+`, `-` or `.`. Note that `localhost:8080/page` therefore counts as having the scheme `localhost`; write `http://localhost:8080/page`.

Detection runs in this order:
1. If it starts with `www.` → prepend `https://` (checked first, so `www.example.com:8080/x` works)
2. If it has an explicit scheme → leave it unchanged
3. If it matches the email pattern → prepend `mailto:`
4. Otherwise → treat as a relative URL

#### Unsafe Schemes

Some schemes run code or carry whole documents instead of pointing somewhere. A URL with the scheme `javascript:`, `vbscript:` or `data:`, in any letter case, is an `unsafe-url` error. So is a URL containing an ASCII control character (U+0000 to U+001F, or U+007F), because browsers silently remove some of them. This applies to every URL: links, self-links, images and quote sources.

```
[click]:javascript:alert(1)
```

**Result:** Error `unsafe-url` — raw HTML is never passed through, and neither is script disguised as a link.

#### Unknown Schemes

Apart from the unsafe schemes above, OireMark does not validate or restrict URL schemes. Custom and future protocols work automatically:

```
[Open in app]:myapp://action/123
[Join call]:zoommtg://zoom.us/join?confno=123
```

### Link Targets

Parsers MUST NOT add a `target` attribute by default: whether a link opens a new window is the reader's choice, and unexpected new windows disorient screen reader users. Implementations MAY offer an option to open web links in a new window. If they do, they SHOULD add `rel="noopener"`.

### Mentions

Links with text starting with `@` are treated as mentions and receive a `mention` class for styling:

```
[@Menelion]:https://dragonscave.space/@Menelion
[@jack]:https://bsky.app/profile/jack.bsky.social
```

**HTML output:**

```html
<a href="https://dragonscave.space/@Menelion" class="mention">@Menelion</a>
<a href="https://bsky.app/profile/jack.bsky.social" class="mention">@jack</a>
```

This applies to any link where the display text begins with `@`, regardless of the URL structure.

### Link Text with Formatting

Links may contain inline formatting in their text:

```
[*Bold link text*]:https://example.com
[Visit _Example_]:https://example.com
```

**HTML output:**

```html
<a href="https://example.com"><strong>Bold link text</strong></a>
<a href="https://example.com">Visit <em>Example</em></a>
```

### Examples

```
[Visit our site]:www.example.com
[Contact support]:hello@example.com
[Call us]:tel:+33123456789
[Join on WhatsApp]:https://wa.me/33123456789
[Read more]:/articles/details
[Back to top]:#top
[@OireMark]:https://github.com/OireMark
```

**HTML output:**

```html
<a href="https://www.example.com">Visit our site</a>
<a href="mailto:hello@example.com">Contact support</a>
<a href="tel:+33123456789">Call us</a>
<a href="https://wa.me/33123456789">Join on WhatsApp</a>
<a href="/articles/details">Read more</a>
<a href="#top">Back to top</a>
<a href="https://github.com/OireMark" class="mention">@OireMark</a>
```

### Self-Linking URLs

When the URL itself should be the link text:

```
[www.example.com]
[hello@example.com]
[https://example.com]
```

**HTML output:**

```html
<a href="https://www.example.com">www.example.com</a>
<a href="mailto:hello@example.com">hello@example.com</a>
<a href="https://example.com">https://example.com</a>
```

The display text preserves what the user wrote (e.g., `www.example.com`), while the `href` contains the normalized URL.

A bracketed text is a self-link **only** if it has an explicit scheme, starts with `www.`, or is an email address. Anything else stays literal text, so ordinary bracketed prose is safe:

```
He said it was "irregardless" [sic].
As shown in [1], the result holds [citation needed].
```

Relative paths and anchors always need link text: `[About]:/about`, not `[/about]`.

### Invalid Syntax

```
[]:https://example.com
```

Empty link text renders literally (malformed).

## 8. Images

### Basic Image

```
![Alt text]:https://example.com/image.png
```

**HTML:** `<img src="https://example.com/image.png" alt="Alt text">`

Alt text is plain text: escapes are processed, and formatting markers are removed while their text is kept, so a screen reader never reads out asterisks. `![The *new* logo]:logo.png` gives `alt="The new logo"`.

`![Alt text]` or `![Alt text]{300x200}` with no `:url` after it is not an image and renders literally.

### With Dimensions

Dimensions go in braces between the alt text and the URL, the same way `{#id}` follows a heading:

```
![Alt text]{300x200}:https://example.com/image.png
![Alt text]{300}:https://example.com/image.png
![Alt text]{x200}:https://example.com/image.png
```

- `{300x200}` — width × height in pixels
- `{300}` — width only, height auto
- `{x200}` — height only, width auto

**HTML:**

```html
<img src="https://example.com/image.png" alt="Alt text" width="300" height="200">
<img src="https://example.com/image.png" alt="Alt text" width="300">
<img src="https://example.com/image.png" alt="Alt text" height="200">
```

Dimensions are positive whole numbers and the separator is a lowercase `x`. Anything else inside the braces is an error. Alt text is never inspected for dimensions, so `![Photo from 2024]:url` simply has the alt text "Photo from 2024".

### Decorative Images

Empty alt text marks an image as decorative:

```
![]:https://example.com/divider.png
```

**HTML:** `<img src="https://example.com/divider.png" alt="">`

Use this only for images that carry no information.

### Linked Image

```
[![Alt text]:https://example.com/image.png]:https://example.com
```

**HTML:**

```html
<a href="https://example.com">
  <img src="https://example.com/image.png" alt="Alt text">
</a>
```

The image's alt text becomes the link's name. A linked image with empty alt text and no other link text is an error, because the link would have no name.

### Image URLs

Image URLs follow the same auto-detection rules as links:

```
![Logo]:www.example.com/logo.png
```

**HTML:** `<img src="https://www.example.com/logo.png" alt="Logo">`

## 9. Lists

A list marker MUST be followed by a space and some content. A line such as `*bold* word` or `#hashtag` is therefore a paragraph, not a list item, and so is a lone `*`.

`*` and `-` are the same bulleted type and may be mixed freely at the top level. Nested levels and ancestry paths always use `*` (`**`, `#*`), so a nested marker never looks like a horizontal rule. A top-level `-` item counts as `*` when matching paths: `- a` followed by `** b` is valid.

### Bulleted (Unordered)

```
* Item one
* Item two
- Also valid
- Another item
```

**HTML:** `<ul><li>Item one</li><li>Item two</li></ul>`

### Numbered (Ordered)

```
# Item one
# Item two
```

Or with explicit numbers:

```
1. Item one
2. Item two
```

**HTML:** `<ol><li>Item one</li><li>Item two</li></ol>`

### Starting Number

An explicit number on the first item sets where the list starts:

```
5. Fifth step
6. Sixth step
```

**HTML:** `<ol start="5"><li>Fifth step</li><li>Sixth step</li></ol>`

A list whose first item uses `#` starts at 1. When the start is 1, the `start` attribute is omitted. `0.` is a valid start, and leading zeros carry no meaning (`05.` is 5).

### Mixing `#` and Explicit Numbers

`#` and explicit numbers may be mixed in one list. A `#` item takes the next number. An explicit number that equals the next number continues the list normally:

```
1. Apples
# Pears
# Plums
4. Oranges
```

**HTML:** `<ol><li>Apples</li><li>Pears</li><li>Plums</li><li>Oranges</li></ol>`

An explicit number that differs from the next number continues the same list from that number, and the parser MUST warn:

```
1. Apples
# Pears
7. Plums
# Oranges
```

**HTML:** `<ol><li>Apples</li><li>Pears</li><li value="7">Plums</li><li>Oranges</li></ol>` (Oranges is number 8)

**Warning:** `List item number 7 does not follow 2 (line 3)`

### List Item Content

List items may contain inline formatting:

```
* This is *bold* and _italic_
* Item with `code` and [a link]:https://example.com
```

### Continuation Lines

A line without a list marker directly after a list item continues that item after a line break, the same way a single newline works in a paragraph:

```
* Oire Software
12 Main Street
Springfield
* Another item
```

**HTML:**

```html
<ul>
  <li>Oire Software<br>
  12 Main Street<br>
  Springfield</li>
  <li>Another item</li>
</ul>
```

A line that begins another block element (a heading, table row, block tag, short form quote, definition marker, code fence or horizontal rule) does not continue the item; it ends the list.

### Nested Lists (Same Type)

Repeat the marker:

```
* Level 1
** Level 2
*** Level 3

# Level 1
## Level 2
### Level 3

1. First
1.1. Nested
1.2. Another nested
2. Second
```

**Note:** A trailing dot is required on nested numbers (`1.1.` not `1.1`) to distinguish them from decimals.

In a nested explicit number, the last component is the item's number at its level and follows the same rules as top-level numbers. The earlier components are there for the reader; parsers SHOULD warn when they do not match the parent items' numbers.

### Nested Lists (Mixed Types)

Use ancestry-path markers. Read left-to-right as outer-to-inner:

```
# Numbered item
#* Bullet inside numbered
#*# Numbered inside bullet inside numbered
* Bullet item
*# Numbered inside bullet
```

**Example:**

```
# Shopping
#* Milk
#* Eggs
#* Bread
# Chores
#* Call mom
```

**HTML:**

```html
<ol>
  <li>Shopping
    <ul>
      <li>Milk</li>
      <li>Eggs</li>
      <li>Bread</li>
    </ul>
  </li>
  <li>Chores
    <ul>
      <li>Call mom</li>
    </ul>
  </li>
</ol>
```

A top-level marker of a different type (for example `*` after a `#` list) ends the current list and starts a new one.

A nested marker MUST have a parent: its path without the last character must match the item directly above it at that level. An `invalid-nesting` error is reported for a level skipped (`*` followed by `***`), for a nested marker with no parent (a list starting with `**`), or for a path that does not match (`# a` followed by `*# b`).

### List Style Types

Add a hint at the first item:

```
#(A) First item
# Second item
# Third item
```

**HTML:** `<ol type="A">...</ol>`

**Supported hints:** `(1)` default, `(A)`, `(a)`, `(I)`, `(i)`

- `(1)` is the default and adds no `type` attribute.
- A hint is allowed only on the first item of a `#` list, at any nesting level (`##(a)`). Anywhere else, including after an explicit number, the marker is not followed by a space, so the line is not a list item: `# a` followed by `#(A) b` is one item whose text continues on a second line.

### List Termination

A blank line ends the current list, as does a line beginning another block element (see Continuation Lines). Multi-paragraph list items are not supported in v1.

## 11. Tables

### Basic Table

```
|| Name || Age || City ||
| Alice | 30 | Paris |
| Bob | 25 | London |
```

- `||` — header cell
- `|` — regular cell

**HTML:**

```html
<table>
  <thead>
    <tr><th scope="col">Name</th><th scope="col">Age</th><th scope="col">City</th></tr>
  </thead>
  <tbody>
    <tr><td>Alice</td><td>30</td><td>Paris</td></tr>
    <tr><td>Bob</td><td>25</td><td>London</td></tr>
  </tbody>
</table>
```

If the first row consists only of `||` cells, it is the header row (`<thead>`), and its cells get `scope="col"`.

### Row Headers

A `||` cell in any other row is a row header and gets `scope="row"`:

```
|| Day || Opens || Closes ||
|| Monday | 9:00 | 18:00 |
|| Saturday | 10:00 | 14:00 |
```

**HTML:**

```html
<table>
  <thead>
    <tr><th scope="col">Day</th><th scope="col">Opens</th><th scope="col">Closes</th></tr>
  </thead>
  <tbody>
    <tr><th scope="row">Monday</th><td>9:00</td><td>18:00</td></tr>
    <tr><th scope="row">Saturday</th><td>10:00</td><td>14:00</td></tr>
  </tbody>
</table>
```

### Tables Without Headers

```
| Alice | 30 |
| Bob | 25 |
```

Produces `<table><tbody>...</tbody></table>` with no `<thead>`. A table whose only row is the header row produces a `<thead>` and no `<tbody>`.

### Rows

- A row is a line starting with `|` or `||`.
- The delimiter at the end of a row is optional. If present, it only closes the last cell and never creates an empty cell, so `| a | b` and `| a | b |` are the same row, and `| a ||` is one regular cell.
- An empty cell is written with a space, `| |`. Two delimiters with nothing between them are always one `||` header delimiter.
- A table ends at the first line that is not a row.

### Cell Spans

Braces directly after a cell's delimiter give the cell a span, written like image dimensions: columns × rows.

- `|{2} text` — spans 2 columns (`colspan="2"`)
- `|{x3} text` — spans 3 rows (`rowspan="3"`)
- `|{2x3} text` — both

The same works for header cells (`||{2} Group`). In the header row, a span follows the alignment marker, if any: `||><{2} Group`. With whitespace between the delimiter and the braces, `| {2}` is ordinary cell text.

Spans are positive whole numbers with a lowercase `x`. A span of 1 adds no attribute. Anything else inside the braces, a row span in the header row, a row span reaching past the last row, or row spans that leave a later row with no slot to write a cell in, is an `invalid-span` error, reported on the row containing the span.

An alignment marker on a header cell that spans columns applies to every column it covers.

**Width rule:** the parser places cells on a grid, left to right, skipping slots already filled by a row span from above. Every row MUST come out as wide as the first row, counting its column spans and the slots filled from above. A row that is wider or narrower is an `uneven-table-row` error, so a forgotten or extra cell is always caught.

```
|| Day || Shift || Hours ||
||{x2} Monday | Morning | 4 |
| Evening | 3 |
|| Total |{2} 7 |
```

The third row has only two cells written, because Monday fills its first slot.

**HTML:**

```html
<table>
  <thead>
    <tr><th scope="col">Day</th><th scope="col">Shift</th><th scope="col">Hours</th></tr>
  </thead>
  <tbody>
    <tr><th scope="row" rowspan="2">Monday</th><td>Morning</td><td>4</td></tr>
    <tr><td>Evening</td><td>3</td></tr>
    <tr><th scope="row">Total</th><td colspan="2">7</td></tr>
  </tbody>
</table>
```

### Column Alignment

Alignment markers in header row cells apply to the entire column:

| Marker | Alignment | Mnemonic |
|--------|-----------|----------|
| `\|\|<` | Left | Arrow points left |
| `\|\|>` | Right | Arrow points right |
| `\|\|><` | Center | Arrows point inward |
| `\|\|<>` | Justify | Arrows point outward |

Alignment markers are recognized only in the header row, directly after `||` with no space between; elsewhere these characters are cell content. A column's alignment applies to every cell that starts in that column, row headers included.

**Example:**

```
||< Name ||>< Age ||> Salary ||
| Alice | 30 | €50,000 |
| Bob | 25 | €45,000 |
```

**HTML:**

```html
<table>
  <thead>
    <tr>
      <th scope="col" style="text-align: left">Name</th>
      <th scope="col" style="text-align: center">Age</th>
      <th scope="col" style="text-align: right">Salary</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td style="text-align: left">Alice</td>
      <td style="text-align: center">30</td>
      <td style="text-align: right">€50,000</td>
    </tr>
  </tbody>
</table>
```

### Whitespace in Cells

- Whitespace around cell content is trimmed.
- An empty cell (`| |`) produces an empty `<td>`.
- An escaped space (`| \ |`) is a non-breaking space and is kept.

### Cell Content

- Inline formatting is allowed in cells.
- A `|` inside a code span does not split the cell. Elsewhere, write `\|` for a literal pipe.
- Block elements (lists, code blocks, etc.) are not allowed in cells.

## 12. Blockquotes

### Bracket Form

```
[quote]
Anonymous quote.
[/quote]

[quote Oscar Wilde]
Quote with author only.
[/quote]

[quote]:https://example.com/source
Quote with source URL only.
[/quote]

[quote Oscar Wilde]:https://en.wikipedia.org/wiki/Oscar_Wilde
I can resist everything except temptation.
[/quote]
```

**HTML:**

```html
<blockquote>
  <p>Anonymous quote.</p>
</blockquote>

<figure class="quote">
  <blockquote>
    <p>Quote with author only.</p>
  </blockquote>
  <figcaption>Oscar Wilde</figcaption>
</figure>

<blockquote cite="https://example.com/source">
  <p>Quote with source URL only.</p>
</blockquote>

<figure class="quote">
  <blockquote cite="https://en.wikipedia.org/wiki/Oscar_Wilde">
    <p>I can resist everything except temptation.</p>
  </blockquote>
  <figcaption><a href="https://en.wikipedia.org/wiki/Oscar_Wilde">Oscar Wilde</a></figcaption>
</figure>
```

The source URL follows the same rules as link URLs (Section 7), including auto-detection.

When an author is given, the quote is wrapped in `<figure>` and the author goes in `<figcaption>`, as the HTML standard recommends for attribution. When both an author and a URL are given, the author is also a link to the source, so the source is reachable by everyone and not only through the `cite` attribute.

### Short Form

For simple quotes without attribution, use `>` at line start:

```
> This is a short blockquote.
```

**HTML:** `<blockquote><p>This is a short blockquote.</p></blockquote>`

The `>` MUST be followed by a space, or stand alone on the line. `>text` is an ordinary paragraph.

Inside a short form quote, the text after `> ` is paragraph text only: `> * item` and `> > nested` are quoted text that starts with `*` or `>`, not a list or a nested quote.

### Multi-line Short Quotes

Consecutive lines starting with `> ` continue the same blockquote:

```
> This is the first line.
> This continues the same blockquote.
> And so does this.
```

**HTML:**

```html
<blockquote>
  <p>This is the first line.<br>
  This continues the same blockquote.<br>
  And so does this.</p>
</blockquote>
```

### Paragraphs in Short Quotes

A line containing only `>` creates a paragraph break within the blockquote:

```
> First paragraph of the quote.
>
> Second paragraph of the quote.
```

**HTML:**

```html
<blockquote>
  <p>First paragraph of the quote.</p>
  <p>Second paragraph of the quote.</p>
</blockquote>
```

### Short Quote Termination

A line not starting with `>` ends the blockquote:

```
> This is quoted.
This is not quoted — new paragraph outside the blockquote.
```

### Inline Formatting in Quotes

Both quote forms may contain inline formatting:

```
> This is *bold* and _italic_ in a quote.

[quote]
This is also *bold* and _italic_.
[/quote]
```

### Short Form Limitations

Short form quotes cannot include:
- Attribution (use bracket form for attributed quotes)
- Source URLs (use bracket form)
- Nested block elements other than paragraphs

### Allowed Content (Bracket Form)

Paragraphs, lists, code blocks, inline formatting. Nested blockquotes are not allowed.

```
[note]
General informational note.
[/note]

[note Mind the gap]
Doors open on the left.
[/note]
```

**HTML:**

```html
<div role="note" class="note">
  <p>General informational note.</p>
</div>

<div role="note" class="note" aria-labelledby="note-1">
  <p class="note-title" id="note-1">Mind the gap</p>

Text after the tag name is the note's title. It is shown as the first line of the note and also labels it, so sighted and screen reader users get the same title. Paragraphs, lists, inline formatting. No nested notes.

## 15. Definition Lists

### Short Form

A line starting with `; ` is a term. A line starting with `: ` is a definition of the term or terms above it:

```
; Term
: Definition text
; Another term
: Another definition
```

**HTML:**

```html
<dl>
  <dt>Term</dt>
  <dd>Definition text</dd>
  <dt>Another term</dt>
  <dd>Another definition</dd>
</dl>
```

### Rules

- The `;` and `:` markers MUST be followed by a space, so a line starting with `:)` is ordinary text.
- Everything after `; ` is the term, colons included: `; Note: deprecated` is the term "Note: deprecated". There is no one-line `; term : definition` form.
- Several `;` lines in a row give several terms sharing the definitions that follow.
- Several `:` lines in a row give several definitions of the same term or terms.
- A line without a marker directly after a `:` line continues that definition after a line break, the same as list items.
- A `:` line with no term before it is an error. So is a term followed by a blank line or by anything other than another term or a definition.
- Terms and short form definitions contain inline formatting only. For definitions with several paragraphs or code, use the long form.

```
; JPEG
; JPG
: A lossy image format for photographs.
: Pronounced "jay-peg".
```

**HTML:**

```html
<dl>
  <dt>JPEG</dt>
  <dt>JPG</dt>
  <dd>A lossy image format for photographs.</dd>
  <dd>Pronounced "jay-peg".</dd>
</dl>
```

### Long Form (Block)

```
[def Term]
A longer definition that
spans multiple lines.
[/def]
```

**HTML:**

```html
<dl>
  <dt>Term</dt>
  <dd>
    <p>A longer definition that<br>
    spans multiple lines.</p>
  </dd>
</dl>
```

### Grouping

Consecutive definition entries (both short and long form) are grouped into a single `<dl>`. A blank line outside a `[def]` block separates definition lists:

```
; Apple
: A fruit
; Banana
: Another fruit

; Orange
: Yet another fruit
```

**HTML:**

```html
<dl>
  <dt>Apple</dt>
  <dd>A fruit</dd>
  <dt>Banana</dt>
  <dd>Another fruit</dd>
</dl>
<dl>
  <dt>Orange</dt>
  <dd>Yet another fruit</dd>
</dl>
```

### Allowed Content (Long Form)

Paragraphs, lists, inline formatting, code. Anything else is an `invalid-nesting` error.

The term is required: `[def]` without one is a `def-without-term` error. Like every title, the term may contain inline formatting.

## 16. Footnotes

### References in Text

```
Some claim[fn1] and another[fn2] and repeated[fn1].
```

### Footnote Block

```
[fn]
1. First footnote explanation.
2. Second footnote explanation.
[/fn]
```

A document has at most one `[fn]` block, and it MUST be the last element of the document. Only `[comment]` blocks may follow it.

**HTML:**

```html
<p>Some claim<sup><a href="#fn1" id="fnref1" role="doc-noteref">1</a></sup> and another<sup><a href="#fn2" id="fnref2" role="doc-noteref">2</a></sup> and repeated<sup><a href="#fn1" id="fnref1-2" role="doc-noteref">1</a></sup>.</p>

<section class="footnotes" role="doc-endnotes">
  <ol>
    <li id="fn1">First footnote explanation. <a href="#fnref1" role="doc-backlink">↩</a></li>
    <li id="fn2">Second footnote explanation. <a href="#fnref2" role="doc-backlink">↩</a></li>
  </ol>
</section>
```

The back link points to the first reference. Its content is the symbol `↩`, which is a glyph, not a word, so it needs no translation. Implementations MUST let users replace the symbol through configuration.

### Footnote Content

Footnote definitions may contain inline formatting and links:

```
[fn]
1. See the *official documentation* at [example.com]:https://example.com for details.
2. This includes `code samples` and _emphasized text_.
[/fn]
```

### Rules

- Every non-blank line in `[fn]` has the form `N. text`, where `N` is the footnote's label. Any other line is an `invalid-nesting` error. Blank lines between footnotes are allowed. The numbers are labels, not list numbering, so list warnings do not apply.
- Footnotes are output in ascending label order. A label that does not follow the previous one gets a `value` attribute, so the visible number always matches the reference: `<li id="fn3" value="3">`.
- A `[fn1]` reference without a corresponding definition: parser warns and renders it literally.
- A definition that nothing refers to: parser warns and still renders it, without a back link.
- Duplicate definitions (two `1.` entries): parser warns, last definition wins.
- Multiple references to the same footnote are allowed; each gets a unique `id`.
- In a profile without footnotes, a `[fn1]` reference is a `feature-not-in-profile` error, just like the `[fn]` block.

### Future Extension

`[en1]` and `[en]...[/en]` are reserved for endnotes (per-chapter) in future versions.

```

**HTML:**

## 18. Table of Contents

### Basic

```
[toc]
```

Generates a linked list of all headings.

### With Level Range

```
[toc 2-4]
```

Includes only h2, h3, h4. The range is two levels from 1 to 6 joined by a hyphen, the first not greater than the second. A first word made of digits and a hyphen that breaks this rule (`[toc 4-2]`, `[toc 0-3]`) is an `invalid-toc-range` error.

### With Title

```
[toc Contents]
[toc 2-4 Contents]
```

Text after the tag name (and after the range, if any) is the title. It is shown above the list and also names the navigation landmark.

**HTML** (`[toc 2-4 Contents]`):

```html
<nav class="toc" aria-labelledby="toc-1">
  <p class="toc-title" id="toc-1">Contents</p>
  <ol>
    <li><a href="#introduction">Introduction</a>
      <ol>
        <li><a href="#overview">Overview</a></li>
        <li><a href="#goals">Goals</a></li>
      </ol>
    </li>
    <li><a href="#chapter-one">Chapter One</a></li>
  </ol>
</nav>
```

Without a title, the output is `<nav class="toc">` with no label and no title line. As with notes, only titled tables of contents use up `toc-N` IDs.

### Rules

- Nested `<ol>` elements reflect the heading hierarchy. A heading nests under the nearest preceding heading of a higher level, so skipped levels (h2 followed by h4) do not create empty items.
- Entry text is the heading's text with its inline formatting. Links inside a heading are reduced to their text, because a link cannot contain another link.
- All headings in the document count, including those inside `[more]`.
- If no heading matches, the `<nav>` contains only its title line, if any, and no list.

## 20. Comments

Block comments only (no line comments):

```
[comment]
This content will not appear in output.
Can span multiple lines.
[/comment]
```

Comments are stripped entirely from output. Like a bracket code block, a comment ends at the first line consisting of `[/comment]`; anything else, including `[/comment]` after text, is part of the comment. They are allowed anywhere a block tag may start, inside any container, and are removed before the rest of the document is parsed: two paragraph lines with a comment between them are one paragraph with a line break.

## 21. Nesting Rules

### Block Elements That Can Contain Other Blocks

| Container | Allowed children |
|-----------|-----------------|
| `[more]` | All except `[meta]`, `[fn]`, `[toc]` |
| `[quote]` | Paragraphs, lists, code, inline. No nested quotes. |
| `[note]` | Paragraphs, lists, inline. No nested notes. |
| `[def]` | Paragraphs, lists, inline, code. |
| Short form definitions (`;`, `:`) | Inline formatting only. |
| `[fn]` | Numbered list only. |
| `[code]` | None — all content literal. |
| `[comment]` | None — all content ignored. |
| `[lang]` (inline) | Inline only — it produces `<span>`. |
| `[lang]` (block) | All except `[meta]` and `[fn]`, including nested block `[lang]` — it produces `<div>`. |
| Short form quotes (`>`) | Paragraphs, inline formatting only. |
| Table cells | Inline formatting only. No block elements. |

Each row is a complete allow-list: anything not listed is an `invalid-nesting` error, reported on the first line of the inner block. `[comment]` is allowed everywhere (Section 20).

### Nesting Depth

Each container block (`[more]`, `[quote]`, `[note]`, `[def]`, block `[lang]`) and each list level adds one level of depth. A document may nest at most 16 levels deep. The block or list item that would open a 17th level is a `nesting-too-deep` error. The limit is the same in every implementation, so a document that is valid in one parser is valid in all of them.

Limits on the total size of the input are left to the application that calls the parser.

### Titles

Every title written after a tag name may contain inline formatting: note titles, `[more]` titles, quote authors, `[def]` terms and table-of-contents titles. A link in a `[more]` title is reduced to its link text, because the title is itself the control that opens the block.

### Empty Blocks

Empty block elements are valid but produce empty output:

```
[note]
[/note]
```

**HTML:** `<div role="note" class="note"></div>`

Parsers MAY warn about empty blocks.

### Invalid Nesting

Invalid nesting produces a parse error:

```
[note]
[note]
Nested note
[/note]
[/note]
```

**Result:** Error — notes cannot contain notes.

## 22. Parsing Rules

### Strictness

OireMark uses strict parsing. Malformed structure produces errors, not best-effort output. Text that only resembles markup renders literally (see Core Principles).

### Conformance

The conformance test suite in the `tests` directory of the specification repository is part of the specification. Where the suite and this text disagree, it is a bug to be fixed in one of them, not a choice left to implementations.

### Literal Output

These are not errors; the text simply is not markup:

- Overlapping inline formatting (`*_bad overlap*_`)
- Invalid tag casing (`[Note]`)
- Whitespace inside tag brackets (`[ note]`)
- Unpaired or misplaced inline markers
- Unknown tags (`[foo]`, `[/about]`). Only reserved tags are errors.
- Anything that resembles a block marker without matching it exactly (`h2.Title`, `*item`, `>text`)

### Errors

Every error has a stable ID. A parser MUST stop at the first error and report its ID and line number. "First" means first found when reading the document from top to bottom; an error is found on the line where it becomes certain, which is not always the line it reports. An unclosed block, for example, becomes certain only at the end of its container or of the document, so in `[note]` followed by `Text.[/note]` the error is `block-tag-mid-line` on line 2, not `unclosed-block` on line 1. If several errors become certain on the same line, the one listed first in this table is reported. Messages are implementation-specific and SHOULD be written for humans.

| ID | Condition | Reported line |
|----|-----------|---------------|
| `invalid-utf8` | Invalid UTF-8 | Line of the first invalid byte |
| `unclosed-block` | Block tag or code fence never closed | Opening tag or fence |
| `mismatched-tag` | Closing tag doesn't match the open block (`[note]...[/quote]`), or closes nothing | Closing tag |
| `meta-not-first` | `[meta]` not at document start | `[meta]` tag |
| `nesting-too-deep` | More than 16 levels of containers and list levels (Section 21) | The line opening the 17th level |
| `invalid-nesting` | Block not allowed inside its container; nested list marker without a matching parent; invalid line in `[fn]` | First line of the inner block |
| `feature-not-in-profile` | Feature not allowed in the active profile | Where the feature starts; for a newline in the `inline` profile, the line after the break |
| `block-tag-mid-line` | Block tag (opening or closing) with other content on its line, including block `[lang]` | That line |
| `lang-without-code` | `[lang]` with no language code | The tag |
| `def-without-term` | `[def]` with no term | The tag |
| `invalid-toc-range` | Invalid level range in `[toc]` | The tag |
| `invalid-span` | Invalid table cell span | The row containing the span |
| `uneven-table-row` | Table row wider or narrower than the first row | The row |
| `reserved-tag` | Reserved tag used (see Reserved for Future Versions) | The tag |
| `duplicate-id` | Two identical custom IDs | Second occurrence |
| `unsafe-url` | URL with a `javascript:`, `vbscript:` or `data:` scheme, or with an ASCII control character | The URL's line |
| `invalid-image-size` | Invalid image dimensions (`{300X200}`, `{wide}`) | The image |
| `unnamed-linked-image` | Linked image with empty alt text and no other link text | The link |
| `more-without-title` | `[more]` without a title | The tag |
| `definition-without-term` | `:` line with no term before it | The `:` line |
| `term-without-definition` | `;` line not followed by a term or definition | The `;` line |
| `footnote-block-misplaced` | `[fn]` block not last, or more than one | First content after `[/fn]`, or the second `[fn]` |

### Warnings (Non-Fatal)

Warnings also have stable IDs. A parser MUST emit the warnings marked "MUST" and MAY emit the others.

| ID | Condition | Required | Result | Reported line |
|----|-----------|----------|--------|---------------|
| `footnote-undefined` | `[fn1]` without definition | MUST | Render literally | The reference |
| `footnote-unused` | Footnote definition without reference | MUST | Render it | The definition |
| `footnote-duplicate` | Duplicate footnote definition | MUST | Last wins | The later definition |
| `list-number-jump` | List number that does not follow the previous item | MUST | `<li value="N">` | The item |
| `list-number-prefix` | Nested number prefix not matching parent items | SHOULD | Render normally | The item |
| `empty-heading` | Empty heading text | SHOULD | Render normally | The heading |
| `heading-missing-space` | Heading marker with no space after it (`h2.Title`) | SHOULD | Render as a paragraph | That line |
| `meta-unknown-key` | Unrecognized `[meta]` key | SHOULD | Ignore the key | The key's line |
| `empty-block` | Empty block element | MAY | Render normally | Opening tag |
| `profile-mismatch` | Document profile wider than the parser's | MAY | Parser's profile wins | The `profile:` line |

### Whitespace in Tags

No whitespace is allowed directly inside tag brackets:
- `[note]` — valid
- `[ note]`, `[note ]`, `[ note ]` — literal output (not recognized as tags)

### Line-Start Markers

The following are only recognized at the start of a line:

- Headings: `h1.` through `h6.`
- List markers followed by a space: `*`, `-`, `#`, `1.`, `**`, `##`, `#*`, `1.1.`, etc.
- Definition markers followed by a space: `;`, `:`
- Table rows: `|`, `||`
- Horizontal rule: `---`
- Short form quotes: `>`
- Code fences: three or more backticks
- Block tags: `[quote]`, `[note]`, `[more]`, `[def]`, `[code]`, `[fn]`, `[meta]`, `[comment]`, `[toc]`, and block `[lang]`

Mid-line occurrences of line-start markers are literal text (or errors for block tags per Section 2). To start a line with one of these characters as text, escape it: `\# 1 fan`, `1984\. A good year.`

### Raw HTML

HTML tags are **not** passed through. They are escaped:

```
<script>alert('xss')</script>
```

**Output:** `&lt;script&gt;alert('xss')&lt;/script&gt;`

No exceptions. No parser flags for "trusted" input.

The same goes for character references: `&` is always escaped, so `&copy;` typed by an author appears as the six characters `&copy;`, not as ©. Type the character itself instead. Attribute values (URLs, alt text, titles) are escaped as well.

## 23. Parser Profiles

Parser profiles allow platforms to restrict which OireMark features are accepted. This enables a single specification to serve use cases from single-line fields to full document authoring.

### Design Rationale

Rather than maintaining separate specifications for different contexts (forums, blogs, documentation), profiles provide configurable feature sets within a single parser codebase. Features outside the active profile produce errors, maintaining OireMark's strict parsing philosophy.

### Standard Profiles

| Profile | Description | Use Cases |
|---------|-------------|-----------|
| `inline` | Inline formatting on a single line | Titles, captions, names, single-line fields |
| `basic` | Paragraphs, lists, code, quotes | Chat messages, forum posts, comments, blog content |
| `standard` | Most features except document-level | Wiki pages, articles, general documents |
| `full` | All features | Books, technical documentation, specifications |

In the `inline` profile, the output fits inside a single element and is never wrapped in `<p>`. A newline is an error.

### Profile Feature Matrix

| Feature | `inline` | `basic` | `standard` | `full` |
|---------|:--------:|:-------:|:----------:|:------:|
| Inline formatting (`*`, `_`, etc.) | ✓ | ✓ | ✓ | ✓ |
| Links and images | ✓ | ✓ | ✓ | ✓ |
| Escapes | ✓ | ✓ | ✓ | ✓ |
| `[lang]` spans (inline) | ✓ | ✓ | ✓ | ✓ |
| Paragraphs and line breaks | — | ✓ | ✓ | ✓ |
| Lists (all types) | — | ✓ | ✓ | ✓ |
| Code blocks | — | ✓ | ✓ | ✓ |
| Blockquotes (bracket form) | — | ✓ | ✓ | ✓ |
| Short form quotes (`>`) | — | ✓ | ✓ | ✓ |
| Horizontal rules | — | ✓ | ✓ | ✓ |
| Headings | — | — | ✓ | ✓ |
| Tables | — | — | ✓ | ✓ |
| Notes | — | — | ✓ | ✓ |
| Definition lists | — | — | ✓ | ✓ |
| Expandable content (`[more]`) | — | — | ✓ | ✓ |
| Comments | — | ✓ | ✓ | ✓ |
| `[lang]` blocks | — | — | ✓ | ✓ |
| `[meta]` block | — | ✓ | ✓ | ✓ |
| Footnotes | — | — | — | ✓ |
| Table of contents | — | — | — | ✓ |

### Specifying Profiles

**In documents** (any profile except `inline`):

```
[meta]
profile: standard
[/meta]
```

**Via parser configuration** (implementation-specific):

```php
// PHP example
$parser = new OireMarkParser(profile: OireMarkProfile::Basic);
```

```csharp
// C# example
var parser = new OireMarkParser(OireMarkProfile.Basic);
```

### Profile Behavior

When a feature is used that is not allowed in the current profile, the parser MUST produce an error:

```
Error: Headings not allowed in 'basic' profile (line 5)
```

### Profile Precedence

1. If a document contains `[meta]` with a `profile` value, that profile applies.
2. If no document profile is specified, the parser's configured profile applies.
3. If the parser has no configured profile, `full` is the default.

**Conflict handling:** If a document specifies a profile that enables more features than the parser allows, the parser's restriction wins. For example, if a parser is configured for `basic` but the document declares `profile: full`, the parser uses `basic` and MAY warn about the mismatch.

### Custom Profiles

Implementations MAY support custom profiles for edge cases:

```php
// PHP example with custom feature set
$parser = new OireMarkParser(features: [
    OireMarkFeature::InlineFormatting,
    OireMarkFeature::Links,
    OireMarkFeature::Lists,
    OireMarkFeature::Tables,
]);
```

```csharp
// C# example with custom feature set
var parser = new OireMarkParser(new[] {
    OireMarkFeature.InlineFormatting,
    OireMarkFeature.Links,
    OireMarkFeature.Lists,
    OireMarkFeature.Tables,
});
```

Custom profiles MUST be a subset of the `full` profile. Implementations MUST NOT allow features beyond what the specification defines.

### Implementation Requirements

Parsers implementing profile support MUST:

1. Support at least the four standard profiles.
2. Default to `full` if no profile is specified.
3. Produce clear errors identifying the disallowed feature and current profile.
4. Document which profile is active in any public API.

## Summary of Syntax

### Block Elements

| Element | Syntax |
|---------|--------|
| Metadata | `[meta]...[/meta]` |
| Heading | `h1.` through `h6.`, optional `{#id}` |
| Paragraph | Blank line separation |
| Code block | `[code lang]...[/code]` or fenced |
| Table | `\|\| header \|\|` and `\| cell \|`; `\|\|` in a body row is a row header; spans `\|{2}`, `\|{x3}`, `\|{2x3}` |
| Blockquote (bracket) | `[quote Author]:url...[/quote]` |
| Blockquote (short) | `> text` |
| Expandable | `[more Title]...[/more]` (title required) |
| Note | `[note]...[/note]` or `[note Title]...[/note]` |
| Definition (short) | `; term` then `: definition` |
| Definition (long) | `[def Term]...[/def]` |
| Footnote block | `[fn]...[/fn]` (last in document) |
| Table of contents | `[toc]`, `[toc 2-4]`, `[toc Title]`, `[toc 2-4 Title]` |
| Horizontal rule | `---` |
| Comment | `[comment]...[/comment]` |
| Language block | `[lang xx]` + newline + `...[/lang]` |

### List Markers

All list markers are followed by a space.

| Type | Markers |
|------|---------|
| Bulleted | `*`, `-` |
| Numbered | `#`, `1.` (first number sets the start) |
| Nested same | `**`, `##`, `1.1.` |
| Nested mixed | `#*`, `*#`, `#*#`, etc. |
| Style hint | `#(A)`, `#(a)`, `#(I)`, `#(i)` |

### Inline Elements

| Element | Syntax |
|---------|--------|
| Bold | `*text*` |
| Italic | `_text_` |
| Underline | `__text__` |
| Deleted | `-text-` |
| Inserted | `+text+` |
| Subscript | `~text~` |
| Superscript | `^text^` |
| Keyboard | `=text=` |
| Highlight | `==text==` |
| Code | `` `text` ``, or longer backtick runs (Section 5) |
| Link | `[text]:url` or `[url]` |
| Mention | `[@user]:url` |
| Image | `![alt]:url` or `![alt]{300x200}:url` |
| Footnote ref | `[fn1]` |
| Language span | `[lang xx]...[/lang]` (same line) |
| NBSP | `\ ` (backslash, space) |
| Escape | `\` + any ASCII punctuation |

### Table Alignment

| Marker | Alignment |
|--------|-----------|
| `\|\|<` | Left |
| `\|\|>` | Right |
| `\|\|><` | Center |
| `\|\|<>` | Justify |

## Reserved for Future Versions

Using a reserved tag is an error, so that documents written today do not change meaning when a later version defines it.

- `[en1]`, `[en]...[/en]` — endnotes
- `[verse]...[/verse]` — poetry/lyrics with preserved line breaks
- `[center]`, `[right]` — block alignment
- `[figure]`, `[audio]`, `[video]` — media elements
- `[abbr ABBR]...[/abbr]` — abbreviations with expansions
- `[alert]` — deliberately not defined: `role="alert"` is meant for live application messages, not documents. Use `[note Title]`.
