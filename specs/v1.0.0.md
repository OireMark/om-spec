# OireMark Language Specification

**Version:** 1.1.0  
**File Extension:** `.om`  
**Author:** André Polykanine / Oire Software  
**Status:** Stable

---

## Introduction

OireMark is a plain-text formatting language designed for authoring documents ranging from quick notes to wiki-scale documentation and books.

### Core Principles

1. **Explicit over implicit.** Markers are self-describing: `h3.` clearly indicates a level-3 heading.
2. **No invisible syntax.** Unlike some other markup languages, OireMark never requires indentation or counting characters. Trailing spaces have no semantic meaning.
3. **Consistent structure.** Block elements use `[tag]...[/tag]` delimiters throughout.
4. **Strict parsing.** Malformed input produces errors, not guesses. Garbage in, error out.

### Character Encoding

- **UTF-8 is required.** No other encodings are supported.
- **BOM:** If present, parsers must strip it. Output must not contain BOM.
- **Invalid UTF-8:** Parsers must reject the document with an error.

### Case Sensitivity

All OireMark syntax is case-sensitive. Tags must be lowercase:
- `[note]` — valid
- `[Note]` or `[NOTE]` — invalid, render literally

## 1. Document Metadata

Optional block at document start for language, profile, and future extensions:

```
[meta]
lang: uk
profile: standard
title: My Document
author: André Polykanine
[/meta]
```

The `lang` value sets the document's primary language (BCP 47 / ISO 639-1 code). Parsers should output this as the root `lang` attribute.

The `profile` value specifies which parser profile to use (see Section 23). If omitted, parsers use their configured default profile.

### Recognized Keys

| Key | Purpose | Output |
|-----|---------|--------|
| `lang` | Document language | `<html lang="...">` or root element attribute |
| `profile` | Parser profile | Controls feature availability |
| `title` | Document title | `<title>` in `<head>` if generating full HTML |
| `author` | Document author | `<meta name="author">` if generating full HTML |

Implementations may define additional keys. Unrecognized keys should be ignored with a warning.

### Syntax Rules

- One key-value pair per line
- Format: `key: value`
- Keys are case-sensitive and lowercase
- Leading/trailing whitespace around values is trimmed
- Empty lines within `[meta]` are ignored

**Placement:** Must be the first element in the document if present. Content before `[meta]` is an error.

## 2. Whitespace Rules

### Core Principle

In OireMark, **indentation and trailing spaces have no semantic meaning**, but **newlines are significant**.

This ensures:
- No invisible syntax that screen readers cannot announce
- No accidental formatting from copy-paste or editor behavior
- Predictable parsing regardless of indentation style

### Newline Significance

Newlines determine:
- Line breaks within paragraphs (single newline → `<br>`)
- Paragraph boundaries (blank line → new `<p>`)
- List item boundaries
- Block element boundaries

### Block Element Line-Start Requirement

Block-level tags **must begin at the start of a line**. Content before a block tag on the same line is invalid:

```
h2. Valid Heading

Some text [quote]Invalid — block tag mid-line[/quote]
```

The second example produces a parse error.

**Block tags subject to this rule:**
- `[quote]`, `[note]`, `[alert]`, `[more]`, `[def]`, `[code]`, `[fn]`, `[meta]`, `[comment]`, `[toc]`
- Headings (`h1.` through `h6.`)
- List markers (`*`, `-`, `#`, `1.`)
- Table rows (`|`, `||`)
- Horizontal rules (`---`)
- Short form quotes (`>`)

### Inline vs. Block Determination for [lang]

The `[lang]` tag can produce either inline (`<span>`) or block (`<div>`) output based on content structure:

**Inline** — content on the same line as opening tag:

```
Here is [lang fr]texte en français[/lang] in English.
```

**HTML:** `<p>Here is <span lang="fr">texte en français</span> in English.</p>`

**Block** — newline after opening tag:

```
[lang fr]
Ceci est un paragraphe entier en français.
Avec plusieurs lignes.
[/lang]
```

**HTML:**

```html
<div lang="fr">
  <p>Ceci est un paragraphe entier en français.<br>
  Avec plusieurs lignes.</p>
</div>
```

### Block [lang] Rules

When `[lang]` is block-level:
- Must start at line beginning (no preceding content)
- May contain paragraphs, lists, and other block elements allowed in its profile
- Closing `[/lang]` must also be on its own line

**Invalid:**

```
Some text [lang uk]
Текст українською.
[/lang]
```

This produces an error — block `[lang]` has content before it on the line.

### Indentation Is Ignored

These are equivalent:

```
[note]
This is a note.
[/note]
```

```
[note]
    This is a note.
[/note]
```

Both produce identical output. The indentation is not preserved or meaningful.

**Exception:** Inside `[code]` blocks, all whitespace including indentation is preserved literally.

## 3. Headings

```
h1. Main Title
h2. Subtitle
h3. Section Heading
h4. Subsection
h5. Minor Heading
h6. Smallest Heading
```

### Custom IDs

```
h2. My Section {#custom-id}
```

**HTML output:**

```html
<h2 id="custom-id">My Section</h2>
```

### Auto-Generated IDs

If no custom ID is provided, parsers should generate a slug from heading text:

```
h2. Hello World
```

**HTML output:**

```html
<h2 id="hello-world">Hello World</h2>
```

**Slugification rules:**
- Lowercase
- Replace spaces with hyphens
- Remove non-alphanumeric characters (except hyphens)
- Collapse multiple hyphens
- If duplicate, append `-2`, `-3`, etc.

### Inline Formatting in Headings

Headings may contain inline formatting:

```
h2. Introduction to *OireMark*
```

**HTML:** `<h2 id="introduction-to-oiremark">Introduction to <strong>OireMark</strong></h2>`

Note: Formatting markers are stripped when generating the slug.

## 4. Paragraphs and Line Breaks

- **Single line break** → `<br>`
- **Blank line** (two or more consecutive newlines) → new `<p>`
- **Multiple blank lines** → collapse to single paragraph break

```
This is line one.
This is line two, same paragraph, with a line break before it.

This is a new paragraph.
```

**HTML output:**

```html
<p>This is line one.<br>
This is line two, same paragraph, with a line break before it.</p>
<p>This is a new paragraph.</p>
```

## 5. Inline Formatting

| Syntax | Element | HTML |
|--------|---------|------|
| `*bold*` | Strong | `<strong>bold</strong>` |
| `_italic_` | Emphasis | `<em>italic</em>` |
| `__underline__` | Underline | `<u>underline</u>` |
| `-deleted-` | Deletion | `<del>deleted</del>` |
| `+inserted+` | Insertion | `<ins>inserted</ins>` |
| `~subscript~` | Subscript | `<sub>subscript</sub>` |
| `^superscript^` | Superscript | `<sup>superscript</sup>` |
| `=key=` | Keyboard | `<kbd>key</kbd>` |
| `==highlight==` | Mark | `<mark>highlight</mark>` |
| `` `code` `` | Code | `<code>code</code>` |

### Nesting

Inline formats may nest if properly paired:

```
*_bold italic_*
```

**HTML:** `<strong><em>bold italic</em></strong>`

### Strict Pairing

Overlapping markers are invalid and render literally:

```
*_bad overlap*_
```

**Output:** Literal `*_bad overlap*_`

### Marker Boundaries

Formatting markers must be adjacent to content (no spaces):
- `*bold*` — valid
- `* not bold *` — literal (spaces inside markers)
- `*also not bold *` — literal (space before closing marker)

### Precedence

- Inline code (backticks) takes highest precedence. Content inside backticks is never parsed for other formatting.
- Other inline formats are parsed left-to-right, innermost first.

## 6. Escaping

Use backslash `\` to escape any special character:

```
\*not bold\*
\[not a tag\]
This is a backslash: \\
Code with backtick: `\``
```

### Special Escapes

| Syntax | Output | Use case |
|--------|--------|----------|
| `\_` | Non-breaking space | Number grouping: `10\_000`, empty table cells |

### Escaped Characters

`*`, `_`, `~`, `^`, `+`, `-`, `=`, `` ` ``, `\`, `[`, `]`, `!`, `|`, `#`, `>`

### Literal Backslash Sequences

`\n`, `\t`, and other letter sequences are literal (backslash + letter). They do not produce newlines or tabs.

## 7. Links

### Basic Syntax

```
[Link text]:url
[url]
```

### URL Handling

OireMark auto-detects and normalizes common URL patterns so users don't need to know technical protocols.

#### Auto-Detection Rules

| User writes | Parser normalizes to | Example |
|-------------|---------------------|---------|
| `www.example.com` | `https://www.example.com` | `[Visit site]:www.example.com` |
| Email address | `mailto:address` | `[Contact us]:hello@example.com` |
| Explicit scheme | Unchanged | `[Call]:tel:+1234567890` |
| Relative path | Unchanged | `[About]:/about` |
| Anchor | Unchanged | `[Top]:#top` |

#### Email Detection

An email address is detected when:
- Contains exactly one `@`
- Has non-empty text before the `@`
- Has text after `@` containing at least one `.`

Examples that trigger email detection:
- `hello@example.com` → `mailto:hello@example.com`
- `support@mail.company.org` → `mailto:support@mail.company.org`

Examples that do NOT trigger email detection:
- `@mention` — no text before `@`
- `price@50` — no `.` after `@`
- `mailto:hello@example.com` — already has scheme

#### Scheme Categories

| Category | Schemes | HTML Output |
|----------|---------|-------------|
| Web | `http://`, `https://` | `target="_blank" rel="noopener"` |
| App handlers | `mailto:`, `tel:`, `sms:`, `ftp://`, `ftps://`, and any custom scheme (e.g., `whatsapp://`, `slack://`, `zoommtg://`) | No target attribute |
| Local | Relative paths (`/page`, `./page`), anchors (`#section`) | No target attribute |

#### Scheme Detection

A URL has an explicit scheme if it matches the pattern: `word:` or `word://` at the start (e.g., `https://`, `mailto:`, `tel:`, `custom://`).

If no scheme is detected:
1. If it starts with `www.` → prepend `https://`
2. If it matches email pattern → prepend `mailto:`
3. Otherwise → treat as relative URL

#### Unknown Schemes

OireMark does not validate or restrict URL schemes. Custom and future protocols work automatically:

```
[Open in app]:myapp://action/123
[Join call]:zoommtg://zoom.us/join?confno=123
```

Both produce working links with no target attribute (app handler behavior).

### Mentions

Links with text starting with `@` are treated as mentions and receive a `mention` class for styling:

```
[@Menelion]:https://dragonscave.space/@Menelion
[@jack]:https://bsky.app/profile/jack.bsky.social
```

**HTML output:**

```html
<a href="https://dragonscave.space/@Menelion" class="mention">@Menelion</a>
<a href="https://bsky.app/profile/jack.bsky.social" class="mention">@jack</a>
```

This applies to any link where the display text begins with `@`, regardless of the URL structure. The `target` and `rel` attributes follow normal scheme rules.

### Link Text with Formatting

Links may contain inline formatting in their text:

```
[*Bold link text*]:https://example.com
[Visit _Example_]:https://example.com
```

**HTML output:**

```html
<a href="https://example.com" target="_blank" rel="noopener"><strong>Bold link text</strong></a>
<a href="https://example.com" target="_blank" rel="noopener">Visit <em>Example</em></a>
```

### Examples

```
[Visit our site]:www.example.com
[Contact support]:hello@example.com
[Call us]:tel:+33123456789
[Join on WhatsApp]:https://wa.me/33123456789
[Read more]:/articles/details
[Back to top]:#top
[@OireMark]:https://github.com/OireMark
```

**HTML output:**

```html
<a href="https://www.example.com" target="_blank" rel="noopener">Visit our site</a>
<a href="mailto:hello@example.com">Contact support</a>
<a href="tel:+33123456789">Call us</a>
<a href="https://wa.me/33123456789" target="_blank" rel="noopener">Join on WhatsApp</a>
<a href="/articles/details">Read more</a>
<a href="#top">Back to top</a>
<a href="https://github.com/OireMark" target="_blank" rel="noopener" class="mention">@OireMark</a>
```

### Self-Linking URLs

When the URL itself should be the link text:

```
[www.example.com]
[hello@example.com]
[https://example.com]
```

**HTML output:**

```html
<a href="https://www.example.com" target="_blank" rel="noopener">www.example.com</a>
<a href="mailto:hello@example.com">hello@example.com</a>
<a href="https://example.com" target="_blank" rel="noopener">https://example.com</a>
```

Note: The display text preserves what the user wrote (e.g., `www.example.com`), while the `href` contains the normalized URL.

### Invalid Syntax

```
[]:https://example.com
```

Empty link text renders literally (malformed).

## 8. Images

### Basic Image

```
![Alt text]:https://example.com/image.png
```

**HTML:** `<img src="https://example.com/image.png" alt="Alt text">`

### With Dimensions

```
![Alt text 300x200]:https://example.com/image.png
![Alt text 300]:https://example.com/image.png
```

- `300x200` — width × height in pixels
- `300` — width only, height auto

**HTML:**

```html
<img src="https://example.com/image.png" alt="Alt text" width="300" height="200">
<img src="https://example.com/image.png" alt="Alt text" width="300">
```

### Dimension Parsing

Dimensions are detected at the end of alt text as:
- `WIDTHxHEIGHT` or `WIDTHxHEIGHT` (case-insensitive `x` or `X`)
- `WIDTH` alone or `WIDTHx`(number at end preceded by space, optionally followed by `x`)
- ` xHEIGHT` (number at end preceded by space and `x`)

Parser normalizes `X` to lowercase `x`.

**Ambiguous cases:**

```
![Photo from 2024]:url
```

`2024` can be treated as width. To avoid it, put a space at the end:

```
![Photo from 2024 ]:url
```

Alt text is "Photo from 2024", no dimensions.

### Linked Image

```
[![Alt text]:https://example.com/image.png]:https://example.com
```

**HTML:**

```html
<a href="https://example.com" target="_blank" rel="noopener">
  <img src="https://example.com/image.png" alt="Alt text">
</a>
```

### Image URLs

Image URLs follow the same auto-detection rules as links:

```
![Logo]:www.example.com/logo.png
```

**HTML:** `<img src="https://www.example.com/logo.png" alt="Logo">`

## 9. Lists

### Bulleted (Unordered)

```
* Item one
* Item two
- Also valid
- Another item
```

**HTML:** `<ul><li>Item one</li><li>Item two</li></ul>`

### Numbered (Ordered)

```
# Item one
# Item two
```

Or with explicit numbers:

```
1. Item one
2. Item two
```

**HTML:** `<ol><li>Item one</li><li>Item two</li></ol>`

### List Item Content

List items may contain inline formatting:

```
* This is *bold* and _italic_
* Item with `code` and [a link]:https://example.com
```

### Nested Lists (Same Type)

Repeat the marker:

```
* Level 1
** Level 2
*** Level 3

# Level 1
## Level 2
### Level 3

1. First
1.1. Nested
1.2. Another nested
2. Second
```

**Note:** Trailing dot required on nested numbers (`1.1.` not `1.1`) to distinguish from decimals.

### Nested Lists (Mixed Types)

Use ancestry-path markers. Read left-to-right as outer-to-inner:

```
# Numbered item
#* Bullet inside numbered
#*# Numbered inside bullet inside numbered
* Bullet item
*# Numbered inside bullet
```

**Example:**

```
# Shopping
#* Milk
#* Eggs
#* Bread
# Chores
#* Call mom
```

**HTML:**

```html
<ol>
  <li>Shopping
    <ul>
      <li>Milk</li>
      <li>Eggs</li>
      <li>Bread</li>
    </ul>
  </li>
  <li>Chores
    <ul>
      <li>Call mom</li>
    </ul>
  </li>
</ol>
```

### List Style Types

Add a hint at the first item:

```
#(A) First item
# Second item
# Third item
```

**HTML:** `<ol type="A">...</ol>`

**Supported hints:** `(1)` default, `(A)`, `(a)`, `(I)`, `(i)`

### List Termination

A blank line (paragraph break) ends the current list. Multi-paragraph list items are not supported in v1.

## 10. Code Blocks

### Bracket Form

```
[code python]
def hello():
    print("Hello, world!")
[/code]
```

### Fenced Form

````
```python
def hello():
    print("Hello, world!")
```
````

**HTML (both forms):**

```html
<pre><code class="language-python">def hello():
    print("Hello, world!")
</code></pre>
```

### Rules

- Language identifier is optional.
- All content inside is literal — no parsing of inline formatting or escapes.
- Indentation and whitespace are preserved exactly.

## 11. Tables

### Basic Table

```
|| Name || Age || City ||
| Alice | 30 | Paris |
| Bob | 25 | London |
```

- `||` — header cell
- `|` — regular cell

**HTML:**

```html
<table>
  <thead>
    <tr><th>Name</th><th>Age</th><th>City</th></tr>
  </thead>
  <tbody>
    <tr><td>Alice</td><td>30</td><td>Paris</td></tr>
    <tr><td>Bob</td><td>25</td><td>London</td></tr>
  </tbody>
</table>
```

### Tables Without Headers

```
| Alice | 30 |
| Bob | 25 |
```

Produces `<table><tbody>...</tbody></table>` with no `<thead>`.

### Column Alignment

Alignment markers in header cells apply to entire column:

| Marker | Alignment | Mnemonic |
|--------|-----------|----------|
| `\|\|<` | Left | Arrow points left |
| `\|\|>` | Right | Arrow points right |
| `\|\|><` | Center | Arrows point inward |
| `\|\|<>` | Justify | Arrows point outward |

**Example:**

```
||< Name ||>< Age ||> Salary ||
| Alice | 30 | €50,000 |
| Bob | 25 | €45,000 |
```

**HTML:**

```html
<table>
  <thead>
    <tr>
      <th style="text-align: left">Name</th>
      <th style="text-align: center">Age</th>
      <th style="text-align: right">Salary</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td style="text-align: left">Alice</td>
      <td style="text-align: center">30</td>
      <td style="text-align: right">€50,000</td>
    </tr>
  </tbody>
</table>
```

### Whitespace in Cells

- One space after `|` or `||` is syntax (consumed).
- Additional spaces are preserved.
- Trailing spaces before `|` are trimmed.

### Cell Content

- Inline formatting is allowed in cells.
- Block elements (lists, code blocks, etc.) are not allowed in cells.

## 12. Blockquotes

### Bracket Form

```
[quote]
Anonymous quote.
[/quote]

[quote Oscar Wilde]
Quote with author only.
[/quote]

[quote]:https://example.com/source
Quote with source URL only.
[/quote]

[quote Oscar Wilde]:https://en.wikipedia.org/wiki/Oscar_Wilde
I can resist everything except temptation.
[/quote]
```

**HTML (full example):**

```html
<blockquote cite="https://en.wikipedia.org/wiki/Oscar_Wilde">
  <p>I can resist everything except temptation.</p>
  <footer>— Oscar Wilde</footer>
</blockquote>
```

### Short Form

For simple quotes without attribution, use `>` at line start:

```
> This is a short blockquote.
```

**HTML:** `<blockquote><p>This is a short blockquote.</p></blockquote>`

### Multi-line Short Quotes

Consecutive lines starting with `> ` continue the same blockquote:

```
> This is the first line.
> This continues the same blockquote.
> And so does this.
```

**HTML:**

```html
<blockquote>
  <p>This is the first line.<br>
  This continues the same blockquote.<br>
  And so does this.</p>
</blockquote>
```

### Paragraphs in Short Quotes

A blank `>` line creates a paragraph break within the blockquote:

```
> First paragraph of the quote.
>
> Second paragraph of the quote.
```

**HTML:**

```html
<blockquote>
  <p>First paragraph of the quote.</p>
  <p>Second paragraph of the quote.</p>
</blockquote>
```

### Short Quote Termination

A line not starting with `>` ends the blockquote:

```
> This is quoted.
This is not quoted — new paragraph outside the blockquote.
```

### Inline Formatting in Quotes

Both quote forms may contain inline formatting:

```
> This is *bold* and _italic_ in a quote.

[quote]
This is also *bold* and _italic_.
[/quote]
```

### Short Form Limitations

Short form quotes cannot include:
- Attribution (use bracket form for attributed quotes)
- Source URLs (use bracket form)
- Nested block elements other than paragraphs

### Allowed Content (Bracket Form)

Paragraphs, lists, code blocks, inline formatting. Nested blockquotes are not allowed.

```
[more Click to expand]

```

**HTML:**

```html
<details>
  <summary>Click to expand</summary>
  <p>Hidden content revealed on click.</p>
```

All block elements including headings, lists, tables, code blocks. Cannot contain `[meta]` or `[fn]`.

## 14. Notes and Alerts

### Notes

```
[note]
General informational note.
[/note]

[note tip]
Helpful suggestion.
[/note]

[note warning]
Something could go wrong.
[/note]

[note caution]
Serious — be careful.
[/note]
```

**HTML:**

```html
<div role="note" class="note">General informational note.</div>
<div role="note" class="note tip">Helpful suggestion.</div>
<div role="note" class="note warning">Something could go wrong.</div>
<div role="note" class="note caution">Serious — be careful.</div>
```

**Note types:** `tip`, `warning`, `caution` (or none for generic note).

### Alerts

For urgent, time-sensitive messages that must interrupt the user:

```
[alert]
Your session will expire in 2 minutes!
[/alert]
```

**HTML:**

```html
<div role="alert" class="alert">Your session will expire in 2 minutes!</div>
```

**Use sparingly.** The `alert` role interrupts screen readers immediately.

### Allowed Content

Paragraphs, lists, inline formatting. No nested notes or alerts.

## 15. Definition Lists

### Short Form (Inline)

```
Term:: Definition text
Another term:: Another definition
```

**HTML:**

```html
<dl>
  <dt>Term</dt>
  <dd>Definition text</dd>
  <dt>Another term</dt>
  <dd>Another definition</dd>
</dl>
```

### Long Form (Block)

```
[def Term]
A longer definition that
spans multiple lines.
[/def]
```

**HTML:**

```html
<dl>
  <dt>Term</dt>
  <dd>A longer definition that<br>spans multiple lines.</dd>
</dl>
```

### Grouping

Consecutive definition entries (both short and long form) are grouped into a single `<dl>`:

```
Apple:: A fruit
Banana:: Another fruit

Orange:: Yet another fruit
```

**HTML:**

```html
<dl>
  <dt>Apple</dt>
  <dd>A fruit</dd>
  <dt>Banana</dt>
  <dd>Another fruit</dd>
</dl>
<dl>
  <dt>Orange</dt>
  <dd>Yet another fruit</dd>
</dl>
```

A blank line separates definition lists.

### Allowed Content

Paragraphs, inline formatting, code. No headings or nested definitions.

## 16. Footnotes

### References in Text

```
Some claim[fn1] and another[fn2] and repeated[fn1].
```

### Footnote Block

Place at document end:

```
[fn]
1. First footnote explanation.
2. Second footnote explanation.
[/fn]
```

**HTML:**

```html
<p>Some claim<sup><a href="#fn1" id="fnref1">1</a></sup> and another<sup><a href="#fn2" id="fnref2">2</a></sup> and repeated<sup><a href="#fn1" id="fnref1-2">1</a></sup>.</p>

<section class="footnotes" role="doc-endnotes">
  <ol>
    <li id="fn1">First footnote explanation. <a href="#fnref1" role="doc-backlink">↩</a></li>
    <li id="fn2">Second footnote explanation. <a href="#fnref2" role="doc-backlink">↩</a></li>
  </ol>
</section>
```

### Footnote Content

Footnote definitions may contain inline formatting and links:

```
[fn]
1. See the *official documentation* at [example.com]:https://example.com for details.
2. This includes `code samples` and _emphasized text_.
[/fn]
```

### Rules

- `[fn1]` reference without corresponding definition: parser warns, renders literally.
- Duplicate definitions (two `1.` entries): parser warns, last definition wins.
- Multiple references to same footnote: allowed, each gets unique `id`.

### Future Extension

`[en1]` and `[en]...[/en]` reserved for endnotes (per-chapter) in future versions.

## 17. Language Spans and Blocks

For inline language switches:

```
Here is some [lang ru]текст на русском[/lang] in English.
```

**HTML:**

```html
<p>Here is some <span lang="ru">текст на русском</span> in English.</p>
```

For block-level language sections (newline after opening tag):

```
[lang uk]
Це цілий абзац українською мовою.
З кількома рядками.
[/lang]
```

**HTML:**

```html
<div lang="uk">
  <p>Це цілий абзац українською мовою.<br>
  З кількома рядками.</p>
</div>
```

Use BCP 47 / ISO 639-1 codes: `en`, `uk`, `fr`, `de`, `ru`, `he`, `zh`, etc.

See Section 2 (Whitespace Rules) for complete inline vs. block determination rules.

---

## 18. Table of Contents

### Basic

```
[toc]
```

Generates linked list of all headings.

### With Level Range

```
[toc 2-4]
```

Includes only h2, h3, h4.

**HTML:**

```html
<nav class="toc" aria-label="Table of contents">
  <ol>
    <li><a href="#introduction">Introduction</a>
      <ol>
        <li><a href="#overview">Overview</a></li>
        <li><a href="#goals">Goals</a></li>
      </ol>
    </li>
    <li><a href="#chapter-one">Chapter One</a></li>
  </ol>
</nav>
```

Nested `<ol>` reflects heading hierarchy.

## 19. Horizontal Rule

Three or more hyphens on a line:

```
---
```

**HTML:** `<hr>`

## 20. Comments

Block comments only (no line comments):

```
[comment]
This content will not appear in output.
Can span multiple lines.
[/comment]
```

Comments are stripped entirely from output.

## 21. Nesting Rules

### Block Elements That Can Contain Other Blocks

| Container | Allowed children |
|-----------|-----------------|
| `[more]` | All except `[meta]`, `[fn]`, `[toc]` |
| `[quote]` | Paragraphs, lists, code, inline. No nested quotes. |
| `[note]`, `[alert]` | Paragraphs, lists, inline. No nested notes/alerts. |
| `[def]` | Paragraphs, inline, code. No headings. |
| `[fn]` | Numbered list only. |
| `[code]` | None — all content literal. |
| `[comment]` | None — all content ignored. |
| `[lang]` (inline) | Inline only — it produces `<span>`. |
| `[lang]` (block) | Paragraphs, lists, and other allowed blocks — it produces `<div>`. |
| Short form quotes (`>`) | Paragraphs, inline formatting only. |
| Table cells | Inline formatting only. No block elements. |

### Empty Blocks

Empty block elements are valid but produce empty output:

```
[note][/note]
```

**HTML:** `<div role="note" class="note"></div>`

Parsers may issue a warning for empty blocks.

### Invalid Nesting

Invalid nesting produces a parse error:

```
[note]
[note]Nested note[/note]
[/note]
```

**Result:** Error — notes cannot contain notes.

## 22. Parsing Rules

### Strictness

OireMark uses strict parsing. Malformed input produces errors, not best-effort output.

### Error Conditions

| Condition | Result |
|-----------|--------|
| Unclosed block tag | Error |
| Mismatched tags (`[note]...[/warning]`) | Error |
| Overlapping inline formatting | Literal output |
| Invalid UTF-8 | Error |
| `[meta]` not at document start | Error |
| Invalid nesting | Error |
| Feature not allowed in current profile | Error |
| Invalid tag casing (`[Note]`) | Literal output |
| Block tag not at line start | Error |
| Block `[lang]` with preceding content on line | Error |

### Warnings (Non-Fatal)

| Condition | Result |
|-----------|--------|
| `[fn1]` without definition | Warning, render literally |
| Duplicate footnote definition | Warning, last wins |
| Empty heading text | Warning, valid but discouraged |
| Empty block element | Warning, valid |
| Unrecognized `[meta]` key | Warning, ignore key |

### Whitespace in Tags

No whitespace is allowed inside tag brackets:
- `[note]` — valid
- `[ note]`, `[note ]`, `[ note ]` — literal output (not recognized as tags)

### Line-Start Markers

The following are only recognized at the start of a line:

- Headings: `h1.` through `h6.`
- List markers: `*`, `-`, `#`, `1.`, `**`, `##`, `#*`, etc.
- Table rows: `|`, `||`
- Horizontal rule: `---`
- Definition (short form): `Term::`
- Short form quotes: `>`
- Block tags: `[quote]`, `[note]`, `[alert]`, `[more]`, `[def]`, `[code]`, `[fn]`, `[meta]`, `[comment]`, `[toc]`, and block `[lang]`

Mid-line occurrences of line-start markers are literal text (or errors for block tags per Section 2).

### Raw HTML

HTML tags are **not** passed through. They are escaped:

```
<script>alert('xss')</script>
```

**Output:** `&lt;script&gt;alert('xss')&lt;/script&gt;`

No exceptions. No parser flags for "trusted" input.

## 23. Parser Profiles

Parser profiles allow platforms to restrict which OireMark features are accepted. This enables a single specification to serve use cases from minimal chat formatting to full document authoring.

### Design Rationale

Rather than maintaining separate specifications for different contexts (forums, blogs, documentation), profiles provide configurable feature sets within a single parser codebase. Features outside the active profile produce errors, maintaining OireMark's strict parsing philosophy.

### Standard Profiles

| Profile | Description | Use Cases |
|---------|-------------|-----------|
| `inline` | Inline formatting only | Chat messages, single-line inputs |
| `basic` | Paragraphs, lists, code, quotes | Forum posts, comments, blog content |
| `standard` | Most features except document-level | Wiki pages, articles, general documents |
| `full` | All features | Books, technical documentation, specifications |

### Profile Feature Matrix

| Feature | `inline` | `basic` | `standard` | `full` |
|---------|:--------:|:-------:|:----------:|:------:|
| Inline formatting (`*`, `_`, etc.) | ✓ | ✓ | ✓ | ✓ |
| Links and images | ✓ | ✓ | ✓ | ✓ |
| Escapes | ✓ | ✓ | ✓ | ✓ |
| `[lang]` spans (inline) | ✓ | ✓ | ✓ | ✓ |
| Paragraphs and line breaks | — | ✓ | ✓ | ✓ |
| Lists (all types) | — | ✓ | ✓ | ✓ |
| Code blocks | — | ✓ | ✓ | ✓ |
| Blockquotes (bracket form) | — | ✓ | ✓ | ✓ |
| Short form quotes (`>`) | — | ✓ | ✓ | ✓ |
| Horizontal rules | — | ✓ | ✓ | ✓ |
| Headings | — | — | ✓ | ✓ |
| Tables | — | — | ✓ | ✓ |
| Notes and alerts | — | — | ✓ | ✓ |
| Definition lists | — | — | ✓ | ✓ |
| Expandable content (`[more]`) | — | — | ✓ | ✓ |
| Comments | — | — | ✓ | ✓ |
| `[lang]` blocks | — | — | ✓ | ✓ |
| `[meta]` block | — | — | — | ✓ |
| Footnotes | — | — | — | ✓ |
| Table of contents | — | — | — | ✓ |

### Specifying Profiles

**In documents** (requires `full` profile to parse `[meta]`):

```
[meta]
profile: standard
[/meta]
```

**Via parser configuration** (implementation-specific):

```php
// PHP example
$parser = new OireMarkParser(profile: OireMarkProfile::Basic);
```

```csharp
// C# example
var parser = new OireMarkParser(OireMarkProfile.Basic);
```

### Profile Behavior

When a feature is used that is not allowed in the current profile, the parser must produce an error:

```
Error: Headings not allowed in 'basic' profile (line 5)
```

### Profile Precedence

1. If a document contains `[meta]` with a `profile` value, that profile applies.
2. If no document profile is specified, the parser's configured profile applies.
3. If the parser has no configured profile, `full` is the default.

**Conflict handling:** If a document specifies a profile that enables more features than the parser allows, the parser's restriction wins. For example, if a parser is configured for `basic` but the document declares `profile: full`, the parser uses `basic` and may warn about the mismatch.

### Custom Profiles

Implementations may support custom profiles for edge cases:

```php
// PHP example with custom feature set
$parser = new OireMarkParser(features: [
    OireMarkFeature::InlineFormatting,
    OireMarkFeature::Links,
    OireMarkFeature::Lists,
    OireMarkFeature::Tables,
]);
```

```csharp
// C# example with custom feature set
var parser = new OireMarkParser(new[] {
    OireMarkFeature.InlineFormatting,
    OireMarkFeature.Links,
    OireMarkFeature.Lists,
    OireMarkFeature.Tables,
});
```

Custom profiles must be a subset of the `full` profile. Implementations must not allow features beyond what the specification defines.

### Implementation Requirements

Parsers implementing profile support must:

1. Support at least the four standard profiles.
2. Default to `full` if no profile is specified.
3. Produce clear errors identifying the disallowed feature and current profile.
4. Document which profile is active in any public API.

## Summary of Syntax

### Block Elements

| Element | Syntax |
|---------|--------|
| Metadata | `[meta]...[/meta]` |
| Heading | `h1.` through `h6.`, optional `{#id}` |
| Paragraph | Blank line separation |
| Code block | `[code lang]...[/code]` or fenced |
| Table | `\|\| header \|\|` and `\| cell \|` |
| Blockquote (bracket) | `[quote Author]:url...[/quote]` |
| Blockquote (short) | `> text` |
| Expandable | `[more Title]...[/more]` |
| Note | `[note]...[/note]`, `[note tip]`, `[note warning]`, `[note caution]` |
| Alert | `[alert]...[/alert]` |
| Definition (short) | `Term:: definition` |
| Definition (long) | `[def Term]...[/def]` |
| Footnote block | `[fn]...[/fn]` |
| Table of contents | `[toc]` or `[toc 2-4]` |
| Horizontal rule | `---` |
| Comment | `[comment]...[/comment]` |
| Language block | `[lang xx]` + newline + `...[/lang]` |

### List Markers

| Type | Markers |
|------|---------|
| Bulleted | `*`, `-` |
| Numbered | `#`, `1.` |
| Nested same | `**`, `##`, `1.1.` |
| Nested mixed | `#*`, `*#`, `#*#`, etc. |
| Style hint | `#(A)`, `#(a)`, `#(I)`, `#(i)` |

### Inline Elements

| Element | Syntax |
|---------|--------|
| Bold | `*text*` |
| Italic | `_text_` |
| Underline | `__text__` |
| Deleted | `-text-` |
| Inserted | `+text+` |
| Subscript | `~text~` |
| Superscript | `^text^` |
| Keyboard | `=text=` |
| Highlight | `==text==` |
| Code | `` `text` `` |
| Link | `[text]:url` or `[url]` |
| Mention | `[@user]:url` |
| Image | `![alt]:url` or `![alt 300x200]:url` |
| Footnote ref | `[fn1]` |
| Language span | `[lang xx]...[/lang]` (same line) |
| NBSP | `\_` |
| Escape | `\*`, `\[`, `\>`, etc. |

### Table Alignment

| Marker | Alignment |
|--------|-----------|
| `\|\|<` | Left |
| `\|\|>` | Right |
| `\|\|><` | Center |
| `\|\|<>` | Justify |
